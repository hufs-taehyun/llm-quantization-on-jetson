# 04. 실제 양자화 파일로 기기에서 실행: 속도·메모리·전력과 정확도

실험 [02](../02_llm_quant_confidence/)는 정확도만 쟀고, PyTorch용 실제 커널(torchao)은 이 Orin에서 느려지거나 실패했다.
여기서는 기기용 실행 엔진(llama.cpp, CUDA)으로 **실제로 줄어든 파일(GGUF)** 을 Jetson Orin Nano(8GB)에서 돌려,
줄여서 얻는 것(속도·메모리·에너지)과 잃는 것(정확도)을 같은 파일에서 함께 쟀다.
질문·측정 방법·판단 기준은 실행 전에 [PLAN.md](PLAN.md)로 고정했다(커밋 4ba8e3c).

## 결론
1. **생성 속도는 4비트(Q4_K_M)가 16비트의 약 2배였다.** Qwen 17.4 → 39.9 tok/s(2.3배), SmolLM2 20.0 → 38.7 tok/s(1.9배). 8비트(Q8_0)는 1.7배·1.6배. 5회 범위가 서로 겹치지 않는다.
2. **파일은 1/3, 생성 토큰당 에너지는 절반 이하가 됐다.** 02의 torchao 커널(속도 절반, 에너지 2.6배)과 반대다. 같은 "8비트"라도 실행 엔진에 따라 결과가 정반대였다.
3. **프롬프트 처리 속도는 빨라지지 않았다.** SmolLM2는 4비트에서 오히려 느려졌다(1,698 → 1,227 tok/s).
4. **8비트는 정확도 손실이 거의 없었다.** Qwen은 구분되지 않았고, SmolLM2는 -1.0%p였다.
5. **4비트의 정확도 손실은 모델에 따라 3배 차이가 났다.** Qwen -2.9%p, SmolLM2 -8.5%p. 같은 양자화 방식, 같은 속도 이득인데 치르는 값이 다르다.
6. **02에서 본 방향은 대체로 유지됐다.** 8비트의 확신 오답은 원본과 구분되지 않았고(D1), 4비트는 정확도가 떨어졌으며(D2), 확신 오답은 SmolLM2에서 줄었다(D3, 02와 같은 방향). Qwen의 확신 오답 증가(+1.3%p)는 방향은 같지만 구분되지 않았다.

→ 이 기기에서 Qwen2.5-1.5B는 Q4_K_M이 쓸 만한 선택이고(속도 2.3배에 -2.9%p), SmolLM2-1.7B는 Q8_0까지가 안전하다. "4비트면 된다"는 모델을 재 보기 전에는 말할 수 없다.

- 기기: Jetson Orin Nano 8GB, JetPack 6.2.1, 25W 모드, 화면(GNOME) 켜진 상태
- 실행 엔진: llama.cpp 커밋 `ff6b8d1`, CUDA 12.6 빌드, 모든 층 GPU(`-ngl 99`)
- 모델: 02와 같은 가중치(Qwen2.5-1.5B-Instruct, SmolLM2-1.7B-Instruct)를 `convert_hf_to_gguf.py`로 F16으로 바꾸고 `llama-quantize`로 Q8_0, Q4_K_M 생성

## 결과 1: 속도·메모리·전력
`llama-bench -p 512 -n 128 -r 5`. 속도는 5회 평균 [최소, 최대]. 대기 전력 3.5 W.

| 모델 | 구성 | 생성 tok/s | 프롬프트 처리 tok/s | 메모리 증가 | 전력(GPU 사용 중) | 생성 토큰당 에너지 |
|---|---|---|---|---|---|---|
| Qwen | F16 | 17.4 [17.1, 17.5] | 1,811 [1,216, 2,037] | 4.5 GB | 15.0 W | 0.86 J |
| Qwen | Q8_0 | 29.6 [28.9, 29.7] | 1,828 [1,457, 1,961] | 2.0 GB | 14.3 W | 0.49 J |
| Qwen | Q4_K_M | **39.9 [39.4, 40.1]** | 1,628 [1,559, 1,646] | 1.3 GB | 14.0 W | 0.35 J |
| SmolLM2 | F16 | 20.0 [19.7, 20.1] | 1,698 [1,380, 1,798] | 3.3 GB | 16.1 W | 0.81 J |
| SmolLM2 | Q8_0 | 31.5 [31.4, 31.5] | 1,449 [1,297, 1,488] | 1.5 GB | 15.9 W | 0.51 J |
| SmolLM2 | Q4_K_M | **38.7 [38.2, 38.9]** | 1,227 [1,197, 1,235] | 0.7 GB | 14.7 W | 0.38 J |

- **생성 속도**: 여섯 구성의 5회 범위가 모델 안에서 서로 겹치지 않는다 → 계획의 기준으로 F16 < Q8_0 < Q4_K_M.
- **프롬프트 처리**: Qwen은 세 구성의 범위가 겹쳐 구분되지 않는다. SmolLM2는 F16 > Q8_0·Q4_K_M(범위 안 겹침)으로 **양자화한 쪽이 느렸다.** 한 번에 512토큰을 처리할 때는 계산량이 속도를 정하고, 양자화 가중치를 풀어 쓰는 비용이 더해지는 것으로 추정한다(확인하지 않음). 생성은 토큰 하나마다 가중치 전체를 읽으므로 가중치가 작을수록 빠르다.
- **전력과 에너지는 계획한 방식으로는 쓸 수 없었다.** 계획은 "실행 전체 구간 평균 전력"이었는데, 이 구간에 모델 로딩 시간이 들어가고 로딩 시간이 구성마다 다르다(Qwen F16 251초, Q4_K_M 103초). 그 값(6.0 / 6.7 / 6.0 W, 7.5 / 10.0 / 10.5 W)은 로딩이 길수록 낮게 나와 비교에 쓸 수 없다. 표의 전력은 **사후에** GPU 사용률 50% 이상인 표본만 평균한 값이고, 에너지는 그 전력 ÷ 생성 tok/s다. 프롬프트 처리 구간이 섞여 있어 근사값이다. 두 방식의 값은 모두 [bench/bench_summary.json](bench/bench_summary.json)에 있다.
- **메모리 증가**는 tegrastats RAM 최댓값 − 실행 전 평균이다(CPU·GPU 공유 메모리 전체). 실행 순서와 직전 상태의 영향을 받는 거친 값이다(Qwen F16이 파일이 더 큰 SmolLM2 F16보다 크게 나온 것도 그 때문으로 본다).
- 측정 중 과전류 보호(oc3) 작동 0회, 접합부 온도 45~55℃.

### 실행 방식 교차 확인
- 점검(validation 20문항): llama.cpp F16 판정이 02의 PyTorch FP16 판정과 Qwen 20/20, SmolLM2 20/20 일치(기준 18/20).
- (사후) test 1,144문항 전체: Qwen 99.7%, SmolLM2 99.4% 일치. 프롬프트와 토큰 처리가 두 실행 방식에서 같다고 본다.
- A~D 확률 질량 평균: Qwen 0.9994 이상, SmolLM2 0.994 이상(상위 100개 확률만 받아도 채점에 충분).

## 실행 기록
- **Jetson에서 llama.cpp CUDA 빌드에 약 3시간이 걸렸다.** 어텐션 커널을 차원 조합별로 따로 컴파일해 CUDA 파일이 많다. 처음 `-j4`로 시작했다가 `-j6`으로 이어서 빌드했다. 웹 UI 파일 내려받기는 실패했지만 쓰지 않는 기능이다.
- **SmolLM2 F16 정확도 측정 중 Jetson이 멈춰 스스로 재시작했다(약 190문항째, 저장된 결과 없음, 재실행).** `llama-server`는 지난 프롬프트의 상태를 RAM에 쌓는 캐시의 기본 한도가 8,192MB인데, 이 기기의 전체 메모리(7.6GB)보다 크다. `--cache-ram 0 -np 1`로 끄고 다시 돌리자 여유 메모리가 1,144문항 내내 약 2.05GB로 일정했다. 캐시가 원인이라는 직접 측정(캐시를 켠 채 메모리 추적)은 기기를 다시 멈출 위험 때문에 하지 않았다. Qwen 세 구성은 캐시를 켠 상태(기본값)로 끝났고, 요청마다 `cache_prompt=false`로 보냈으므로 결과에는 영향이 없다고 본다.
- 재실행부터 100문항마다 여유 메모리를 기록하고 600MB 아래면 스스로 멈추게 했다.

## 한계
- 4비트는 Q4_K_M 한 가지만 봤다(Q4_0, imatrix 보정, 다른 비트 수는 범위 밖). 모델 2개, 데이터 1개, 0-shot.
- 속도·전력은 한 보드, 한 세션, 고정 길이(프롬프트 512, 생성 128)에서 잰 값이다. 전력은 보드 전체 기준이고 구간을 나누지 못했다.
- 다음 토큰 확률은 생성 품질 전체를 대표하지 않는다. 긴 답변의 품질은 보지 않았다.

## 재현 (Jetson, ~/pt-venv)
```bash
# 사전: llama.cpp를 ~/llama.cpp에 받아 CUDA로 빌드 (cmake -B build -DGGML_CUDA=ON -DLLAMA_CURL=OFF)
bash make_gguf.sh                  # F16 변환 → Q8_0, Q4_K_M
bash run_bench.sh bench            # 측정 1
python analyze_bench.py --dir bench
python eval_gguf.py --gguf ~/llm/gguf/qwen15-f16.gguf --model ~/llm/qwen15 --name fp16 --out res_qwen15   # w8=Q8_0, w4=Q4_K_M도 같은 방식
python ../02_llm_quant_confidence/analyze.py --dir res_qwen15
# run_all.sh는 위 과정을 사람 없이 이어서 실행한다
```
